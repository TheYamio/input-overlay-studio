# Проверка Input Overlay Studio

Тесты используют синтетические профили, отдельные browser contexts и временные папки данных. Они не должны изменять рабочие настройки. Закройте пользовательский экземпляр Input Overlay Studio перед нативными сценариями: singleton действует для всех копий приложения. Скрипты завершают только собственные дочерние процессы.

## Основной набор

```powershell
pnpm --dir studio test
pnpm --dir studio build
cargo test --locked --manifest-path ws-server/src-tauri/Cargo.toml --lib
cargo build --locked --release --manifest-path ws-server/src-tauri/Cargo.toml
```

`pnpm test` сверяет автоматически сгенерированный native-контракт и запускает unit-тесты. Проверяются версия документа v4, текущие module envelopes, ссылки игр/оверлеев, атомарность, Undo/Redo, резервные копии, будущие версии, неизвестные модули, ограничения JSON, параметры ошибок и локализация. Читатели v1–v3 в приложение не возвращаются.

Для браузерных сценариев выполните `pnpm --dir studio exec playwright install chromium`. Каждый сценарий создаёт собственные данные и закрывает контексты/серверы.

| Команда `pnpm --dir studio …` | Проверяет |
|---|---|
| `test:browser`, `test:editor` | Основные страницы, геометрию, блокировку, текст и импорт |
| `test:workspace`, `test:transforms` | Панели, прокрутку, масштаб, перетаскивание, размеры и отмену жестов |
| `test:shortcuts` | Команды выделения, текстовые сочетания, привязки, конфликты и reload |
| `test:visual`, `test:visual-features`, `test:customization` | Картинки, маски, фон, типографику, состояния кнопок и OBS-синхронизацию |
| `test:shapes`, `test:presets` | SVG, библиотеку, перенос цвета/расположения, описания и ресурсы |
| `test:animation`, `test:schema-animation` | Задержки, свет/движение, наследование и отсутствие постоянного RAF |
| `test:settings-ui`, `test:schema-settings` | Декларативные поля, ограничения, фокус, точный ввод, зависимости и адаптеры |
| `test:module-runtime`, `test:extensible-modules` | Lifecycle, изоляцию ошибок, отключение и возврат доверенной регистрации |
| `test:profiles`, `test:sync` | Явные связи игры/оверлея, расчёты, revision/CAS, конфликт и восстановление |
| `test:localization` | Пакеты, Unicode/IME, RTL, реальные web fonts и независимый язык OBS |

Прежний UI/renderer удалён; названия вспомогательных standalone-компонентов не являются переключателями старого приложения. Тестовые fixtures и контрольные модули исключены из production entry graph.

## Настоящий Windows EXE

`STUDIO_NATIVE_EXE` позволяет выбрать проверяемую сборку. Без него используется `ws-server/src-tauri/target/release/input-overlay-ws.exe`.

- `test:acceptance`: доверенный контрольный модуль с новой числовой настройкой и французским языковым пакетом проходит production Settings Renderer/SettingsService, настоящий native store, backup restore и restart. Проверяются ограничения/Undo/Redo, сохранность Unicode, независимый язык runtime, отказ v1–v3 и отключение/включение без накопления обработчиков.
- `test:language-native`: загрузка всех встроенных языков из собранного EXE, отложенная загрузка каталогов, повтор после ошибки, сохранение выбора после restart и неизменность документа оверлея.
- `test:native`: HTTP/WS/Raw Input, native window, singleton, сохранение, восстановление, изображения, настройки, задержки и работа после закрытия редактора. `STUDIO_NATIVE_RESOURCES=1` добавляет замер дерева процессов.
- `test:extensible-native`: неизвестные/будущие/отключённые модули и ресурсы, текущие capability flags, безопасный отказ невалидной записи, языковые пакеты, restart и защищённый оригинал будущей версии.

Windows CI запускает frontend-регрессии, Rust и нативную архитектурную приёмку после сборки. Ни тестовые модули, ни отчёты не входят в пользовательский ZIP.

## OBS и нагрузка

`test:obs` использует отдельную portable OBS в `.tools/obs-portable`, пустую коллекцию и только Browser Source. Пароли и токены тестовые; desktop/game/audio capture, стрим и запись не создаются. Пользовательская OBS не управляется. Нужна заранее подготовленная portable установка. `STUDIO_OBS_PERF_SECONDS` добавляет замер; обмен использует канонический wire v4.

`test:resources` измеряет production renderer: idle/active, общую картинку, плотную сцену, скрытые метрики, редактор и 25 циклов открытия панелей. Занятость главного потока не равна общему CPU компьютера. `STUDIO_BENCH_ENVELOPES=1` включает канонический wire v4; `STUDIO_BENCH_LABEL` задаёт имя отчёта. Для массовых обновлений задайте `STUDIO_BENCH_CASE=updates`.

В режиме `updates` флаг `STUDIO_BENCH_PROFILE=1` сохраняет CDP CPU profiles, `STUDIO_BENCH_TRACE=1` — timeline traces с работой JS, пересчётом стилей, layout и compositing. Эти диагностические прогоны отмечаются в `instrumentation`; итоговое время сравнивайте отдельно без профилирования. `STUDIO_BENCH_DIST` выбирает замороженный frontend той же версии формата для парного сравнения. Проверка `test:module-runtime` также охватывает сохранение DOM/нажатия при перемещении, изменение языка только по необходимости и пересчёт общей картинки между модулями.

`test:paired` требует `STUDIO_BASELINE_DIR`, указывающий на замороженный архив этапа 0. Он запускает обе production-сборки последовательно в одном Chromium с одинаковыми визуальными данными и одним интервалом синтетического ввода. Фиксирует фактическую частоту, idle, удержание и ожидание press/release delay. Преобразование старого синтетического fixture существует только в тесте и не является поддержкой старых пользовательских файлов.

`test:performance` подаёт 8000 синтетических событий в секунду; `STUDIO_STRESS_SECONDS` задаёт длительность, `STUDIO_STRESS_LABEL` — имя отчёта, `STUDIO_BENCH_DIST` — путь production frontend для парного прогона. Это проверка обработки/ограниченной памяти, не измерение физического polling rate или игровой задержки.

Замеры выполняйте последовательно, без сборок и других тестов в фоне. Working Set суммирует в том числе общие страницы; это не уникальный расход физической RAM. После смены формата откат требует парных снимков кода и данных. Скриншоты, логи и отчёты хранятся отдельно от сборки.

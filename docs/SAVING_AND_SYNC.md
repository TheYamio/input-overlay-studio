# Сохранение и синхронизация

Каждая принятая правка сохраняется локально вместе с версией сервера, от которой началось редактирование. Отправка на сервер происходит через 350 мс после изменения. OBS получает настройки после успешной записи сервером.

## Статусы

- **Saved locally** — черновик записан в браузерное хранилище.
- **Saving…** — сервер ещё не подтвердил запись.
- **Synced to OBS** — сервер подтвердил текущую версию; подключённые OBS-клиенты получают её через WebSocket.
- **Conflict · local draft kept** — на сервере появилась другая версия; локальный черновик сохранён и не заменяется автоматически.
- **Local save failed / Save failed · draft kept** — произошла ошибка. Если локальное хранилище недоступно, используйте экспорт до закрытия редактора.

## Если открыты два редактора

При конфликте можно:

1. Нажать **Export local draft**, чтобы сохранить локальный вариант отдельным JSON.
2. Нажать **Publish local version**, чтобы явно заменить серверную версию своим вариантом. Сервер повторно проверит, что версия не успела измениться.
3. Нажать **Use server version**, чтобы принять серверный вариант. Предыдущий локальный вариант остаётся в Undo в текущем сеансе.

Это выбор целого документа. Автоматического слияния отдельных полей пока нет. Варианты разных клиентов не смешиваются молча.

После отключения и перезапуска локальный черновик публикуется автоматически только если серверная версия не изменилась. Если данные на сервере совпадают с черновиком, повторная запись не требуется. Старый черновик без сведений о базовой версии требует явного выбора при отличающихся серверных данных.

## Восстановление и ограничения

- Настройки и сведения о несинхронизированном черновике записываются одной операцией localStorage.
- Подтверждение записи не заменяет предыдущую резервную копию той же самой конфигурацией.
- Ошибка квоты хранилища не классифицирует корректный старый документ как повреждённый.
- Перед изменением текущего документа резервная копия проверяется чтением. Ошибка копирования останавливает замену.
- Формат документа — v4. Компактный документ ограничен 1 800 000 байт UTF-8; импорт и транспорт — 2 000 000 байт. Экспорт использует компактный JSON, который проходит обратный импорт.
- Секрет соединения и внутренние сведения о синхронизации не попадают в экспорт профилей.
- Запись конфигурации выполняется через временный файл и замену. Обработчик движения не ждёт дисковую блокировку сохранения. Дистанция также записывается через временный файл; ошибки её записи попадают в журнал без событий клавиатуры.
- localStorage и история пока остаются синхронными и хранят изображения внутри документов. Жест ввода/ползунка объединяется в одну операцию Undo; промежуточные допустимые значения сохраняются в локальном черновике. Перенос assets в IndexedDB — отдельная оптимизация.

## Совместимость

Для записи необходимы протокол 5, явный capability contract, поддержка документа v4, module envelope, game links и revision. Старые клиенты и серверы не получают путь обхода проверки. OBS Runtime остаётся читателем. После обновления перезагрузите Studio и Browser Source для загрузки актуальных JS-файлов.

Документ будущей версии не понижается и не перезаписывается defaults: редактор предлагает **Export original JSON**. Для будущего импортируемого файла доступен **Back to current profile**. Локальный несинхронизированный черновик сохраняется. Оригинал слишком большого серверного файла остаётся в папке данных и не передаётся сверх лимита WS. Цепочка будущих миграций начинается с v4; предыдущие преобразования удалены.


## Разработчику

Редактор обращается к `core/settings/`: SettingsService владеет документом, транзакциями, историей, локальным черновиком и синхронизацией. Адаптеры предпочтений и NativeConfig используют прежние ключи и команды. `core/storage.ts` остаётся низкоуровневым адаптером совместимого формата. Чтение/изменение по зарегистрированному ID требует явного адреса области; транзакция проверяет весь документ до фиксации. Подробности API и уведомлений — в [архитектуре](ARCHITECTURE.md).

Протокол 4 дополняет протокол ввода 3:

- `auth_response.studio_revisions = true` включает безопасное сохранение.
- `studio_get` возвращает `studio_config` с `revision` и `config_sequence`.
- `studio_set` обязан содержать `base_revision`, `request_id` и документ.
- `studio_saved` подтверждает только успешно записанный документ и возвращает новую `revision`.
- При устаревшей базе `studio_conflict` возвращает актуальный документ и его версию. Запись не выполняется.
- `studio_error` означает отказ проверки или записи. Текущий документ и его версия не меняются.
- `revision` — SHA-256 канонической сериализации серверного документа; сохраняет значение после рестарта при неизменном документе. Это маркер версии, а не секрет авторизации.
- `studio_capabilities` в auth_response и `studio_client` в auth объявляют независимые версии контракта, протокола, чтения/записи документа, схем модулей и возможностей. Предыдущие флаги сохраняются; Runtime объявляет отсутствие права записи конфигурации.
- `studio_unsupported` сообщает о будущем формате, который сервер сохраняет без преобразования. `original_json` содержит исходный текст, когда он помещается в ограничение транспорта. Сервер отвергает попытки заменить такой файл текущим форматом.
- `config_sequence` упорядочивает сообщения конфигурации в пределах запуска сервера; при новом соединении клиент сбрасывает счётчик. Номер не заменяет сравнение `base_revision`.


После изменения схемы выполните `node scripts/schema-contract.mjs` из `studio`. `pnpm test` проверяет, что контракт не устарел. Rust-валидатор поддерживает используемое подмножество JSON Schema и отвергает неизвестные ключевые слова.

Проверки: `pnpm test`, `pnpm test:sync`, `pnpm test:browser`, `pnpm test:visual`, Rust unit tests, `node scripts/native-test.mjs`, `node scripts/obs-test.mjs`. Native и OBS запускайте последовательно.


## Профили и формат после этапа 9

Поддерживаемая база — документ v4 и протокол 5. Старые документы v1/v2/v3 и пресеты v1 не импортируются. Будущие версии документа защищены от перезаписи и доступны для экспорта оригинала.

DPI/sensitivity/yaw живут в `gameProfiles`; `profiles` содержат оверлеи со ссылкой `gameProfileId`. Выбор игры для редактирования не переключает live-оверлей. Activate game и Activate overlay делают переключение явно. Несколько композиций могут использовать одну игру. Удаление используемой игры требует замены ссылок; операция целиком доступна в Undo.

Экспорт игры содержит только игровую запись. Экспорт оверлея — один оверлей, его игру и используемые ресурсы. Полный Export JSON остаётся резервной копией конфигурации. Токен, Capture-настройки, временный ввод и история редактора в них не включаются.

Текущий браузерный ключ — `input-overlay-studio.document`; файлы пользователя и архивы старых сборок не удаляются при запуске. Очистка исходников удаляет исторические читатели и тестовые ветви, а не личные данные на диске.

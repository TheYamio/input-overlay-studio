# Аудит Input Overlay Studio 0.3.0

Дата: 20 октября 2026 года. Проверяется текущее рабочее дерево, включая незакоммиченные изменения.

Это снимок состояния 0.3.0. После аудита выполнен этап сохранения и синхронизации 0.3.1: ревизии и конфликты, согласованные лимиты, структурная native-валидация, отдельная дисковая блокировка, исправления локальных backup и атомарная запись дистанции. Актуальное поведение описано в [SAVING_AND_SYNC.md](SAVING_AND_SYNC.md). Остальные находки ниже остаются планом последующих этапов; перенос больших assets в IndexedDB также пока не выполнен.

## Вывод

Проект уже имеет работающую основу: нативный захват, отдельный OBS-рендерер, редактор, профили, вычисления чувствительности, изображения на кейкапах и переносимые пресеты. Основные автоматические сценарии проходят. Следующий этап стоит посвятить надёжности сохранения, проверке импортов и удобству редактора, затем расширению визуальных возможностей.

«Все тесты проходят» здесь не означает «все требования проверены». В этом аудите обнаружены случаи, не входящие в существующие тесты. Аппаратную совместимость, задержку до изображения в OBS и длительную работу в играх автоматические браузерные тесты не доказывают.

Исходники приложения в рамках аудита не исправлялись. Добавлены этот отчёт и диагностический скрипт в игнорируемой папке `studio/artifacts`.

Обозначения:

- **P1** — исправить перед следующим публичным выпуском: риск потери изменений или нарушения сохранения.
- **P2** — исправить в ближайшем цикле: неверное поведение в отдельных сценариях.
- **P3** — улучшения удобства, сопровождения и поставки.
- **Воспроизведено** — выполнена отдельная проверка.
- **По коду** — установлен путь возникновения проблемы; полноценный сценарий на оборудовании не запускался.
- **Риск** — требуется измерение или дополнительный эксперимент; не объявляется доказанным сбоем.

## Исправления с наибольшим приоритетом

### 1. P1 — внешний конфиг может уничтожить несохранённые изменения редактора

**По коду.** `studio/src/main.tsx:183–193`, `studio/src/core/connection.ts`, `ws-server/src-tauri/src/ws_server.rs`.

Защита `pending` действует только при первом получении конфигурации после соединения. В дальнейшем входящий документ другого клиента безусловно заменяет текущий документ, отменяет таймер публикации и очищает Undo/Redo.

Сценарий: открыты два редактора; в первом изменён цвет, но ещё не прошло 350 мс; второй отправляет своё изменение. Первый принимает чужой документ, теряет свою правку и историю. После переподключения обратная ситуация: старый локальный документ с `pending` может целиком перезаписать более новые серверные изменения.

**Исправление:** ревизия документа на сервере, отправка `baseRevision`, отказ от слепой перезаписи при конфликте. Для первой версии достаточно сохранить локальный вариант и предложить выбор версии. Не очищать историю без объяснения. OBS-клиент не должен инициировать миграцию через запись конфигурации: сейчас это делает общий `InputConnection`.

**Проверка:** два независимых браузерных контекста, одновременное редактирование, offline-правка, reconnect, две разные версии схемы. Ни один вариант не должен исчезать без возможности восстановления.

### 2. P1 — допустимый документ может не сохраняться и не импортироваться после собственного экспорта

**Воспроизведено.** `studio/src/core/config.ts:60`, `studio/src/main.tsx` (`exportConfig`, `importConfig`), `ws-server/src-tauri/src/studio_store.rs:43–44`.

Frontend считает длину компактной JSON-строки в символах. Backend ограничивает размер форматированного JSON в UTF-8 байтах. Файловый импорт также ограничен байтами файла. Это разные величины.

Пример: два профиля, в каждом 32 клавиатурных модуля по 100 клавиш с допустимой подписью из 100 кириллических символов:

- схема принимает документ;
- компактная строка — 1 133 407 символов;
- WS-запрос — 1 773 698 байт;
- экспорт с отступами — 2 757 245 байт.

Такой документ проходит frontend-проверку, но не помещается в native-лимит 2 MB и не проходит обратный импорт экспортированного файла. Это предельный, но разрешённый схемой сценарий.

**Исправление:** единая политика размера в UTF-8 с учётом транспортной оболочки; компактное хранение либо согласованные лимиты форматированного экспорта. Обязательный тест `export → import` для максимально разрешённого документа, включая кириллицу.

### 3. P1 — сервер сохраняет конфигурации, которые клиент считает повреждёнными

**По коду.** `ws-server/src-tauri/src/studio_store.rs:79` (`valid_document`).

Rust проверяет только оболочку: версию, активный профиль, несколько чисел, количество модулей и часть свойств изображения. Он не проверяет обязательные поля модулей, их типы, цвета, уникальность ID, ссылки на изображения, полную структуру performance и distance.

Авторизованный клиент может сохранить `modules: [{}]` или `performance: {}`. Сервер считает файл допустимым и не включает восстановление, тогда как Studio его отвергает. Это проблема целостности между версиями клиентов и ручными конфигами; обход аутентификации не обнаружен.

**Исправление:** эквивалентная полная схема на Rust или общий контракт с корпусом одинаковых валидных/невалидных примеров для TS и Rust. Отклонять до записи и возвращать конкретное поле ошибки. Не принимать файл за годный backup только на основании слабой проверки оболочки.

### 4. P2 — сохранение держит блокировку, необходимую обработке движения

**По коду; величина задержки не измерена.** `studio_store.rs` (`set`, `add_distance`), `ws_server.rs` (`distributor`).

`set` удерживает mutex документа, пока выполняются чтение старого файла, запись backup и основного файла. `add_distance` требует тот же mutex. Диспетчер ожидает `add_distance` последовательно, поэтому сохранение большого документа может задержать обработку следующих событий, включая клавиши.

`spawn_blocking` освобождает поток Tokio от файловой работы, но не снимает зависимость диспетчера от этой блокировки.

**Исправление:** отдельная сериализация записей и короткая блокировка актуального состояния; DPI активного профиля доступен без ожидания диска. Проверять input latency при непрерывном изменении стилей с большими изображениями и искусственно медленной записью.

### 5. P2 — тяжёлые операции хранения выполняются на каждое изменение поля

**По коду; пользовательские торможения пока не измерены.** `studio/src/main.tsx:116,128–153`, `studio/src/core/storage.ts`.

Каждая правка клонирует документ, проверяет схему, сериализует документ несколько раз, сохраняет предыдущую версию и новую версию в синхронный localStorage. Задержка 350 мс относится только к сетевой отправке. До 60 снимков истории включают изображения. Дополнительно `useRef(loadDocument())` вычисляет `loadDocument()` при каждом рендере, хотя ref использует только первый результат.

**Исправление:** ленивое создание состояния и engine/connection, объединение изменения ползунка в одну операцию Undo, отдельное хранение неизменяемых assets, IndexedDB для больших данных. Если вводится отложенная локальная запись, сохранить гарантию последней правки при немедленном закрытии.

Отдельно исправить `saveDocument`: один `catch` охватывает и парсинг старого документа, и запись backup. Ошибка квоты может ошибочно отправить корректный предыдущий документ в ветку `.invalid`. Разделить проверку валидности и обработку ошибки записи.

## Подтверждённые ошибки импорта и редактора

### 6. P2 — ID с кавычкой ломает перетаскивание

**Воспроизведено.** `studio/src/core/config.ts:8`, `studio/src/main.tsx:64`.

Схема допускает `id: 'quote"id'`, а Preview подставляет ID напрямую в CSS-селектор. `querySelector` выбрасывает исключение. Импорт проходит, но перетаскивание такого модуля работает некорректно.

**Исправление:** DOM-map по ID или безопасное экранирование селектора. Само наличие кавычки не следует объявлять XSS: воспроизведена именно ошибка CSS-селектора.

### 7. P2 — Key gap меняет реальные размеры, но не границы раскладки

**Воспроизведено.** `studio/src/core/skins.ts:6–8`.

При `gap = 0` стандартная клавиатура имеет расчётную ширину 178 и высоту 240, но фактические края клавиш — 186 и 248. Масштабирование модуля и размещение общего изображения используют меньшие размеры.

Следствие: визуал выходит за рамку выделения, покрытие изображения и масштаб по краям становятся неточными.

**Исправление:** вычислять bounds из итоговых геометрий cap после применения gap. Явно определить, меняет ли gap размеры клавиш или расстояния между ними; сейчас название не объясняет поведение. Проверить gap 0/8/30, неодинаковые клавиши и общую картинку.

### 8. P2 — неполные инварианты схемы

**Воспроизведено.** `studio/src/core/config.ts`.

- Модуль с `x = 1920` и ненулевой шириной проходит проверку и оказывается за сценой.
- Повторяющиеся ID модулей внутри пресета полного документа проходят проверку; при применении такого пресета профиль уже не проходит свою проверку.
- У preset ID нет проверки уникальности. Действия через `.find`/`.filter` становятся неоднозначными.

**Исправление:** общие проверки профилей и пресетов; уникальность ID на соответствующем уровне. Для выхода за сцену либо нормализовать координаты при импорте, либо осознанно разрешить это и добавить действие «Вернуть в кадр». Сейчас поля свойств и импорт придерживаются разных правил.

### 9. P2 — валидный Base64 не гарантирует валидную картинку

**Воспроизведено.** `studio/src/core/visual.ts` (`assetSchema`), `studio/src/renderer/scene.ts` (`assetUrl`).

`data:image/png;base64,aGVsbG8=` проходит схему, хотя содержит текст `hello`; декодирование изображения браузером завершается ошибкой. Метаданные width/height также не сверяются с настоящим содержимым файла.

Обычная загрузка через Upload декодирует картинку, а JSON-импорт обходит эту проверку. В результате пользователь получает отсутствующую текстуру без понятной причины.

**Исправление:** единый путь проверки загрузки и импорта: формат, декодирование, фактические размеры, лимит пикселей, нормализация. При повреждённой картинке сообщать имя asset и сохранять возможность восстановить остальной документ.

### 10. P2 — Lock position действует непоследовательно

**По коду.** `studio/src/main.tsx:93`.

Блокировка запрещает drag, resize и кнопки выравнивания, но X/Y/Width/Height остаются редактируемыми. Переключение вида мыши также меняет размеры и иногда координаты.

**Исправление:** единое правило блокировки трансформации. В текущем значении «Lock position» пользователь ожидает сохранения расположения. Проверять все пути изменения, а не только drag.

### 11. P2 — есть настройки без соответствующего эффекта

**По коду.** `studio/src/visual-controls.tsx` (`ModuleAppearance`), `studio/src/renderer/scene.ts`.

Одна форма StyleFields показывается для всех модулей. Distance/Sensitivity/Trail получают настройки нажатия, хотя у них нет поведения нажатой клавиши. Auto-fit реально реализован в renderCaps; текстовые метрики не получают аналогичного подбора размера.

**Исправление:** показывать только применимые поля. Для Distance/Sensitivity добавить явную политику длинного текста: уменьшение, перенос либо обрезка с предпросмотром. Проверить большие шрифты и максимальные подписи.

### 12. P2 — копирование OBS URL не проверяет доступность HTTP

**По коду.** `studio/src/main.tsx` (`copyOBS`), `services/http_server.rs` (`start`).

Достаточно работающего WebSocket, чтобы скопировать URL, даже если HTTP отключён или его порт занят. `HttpServer::start` возвращает объект до результата bind; ошибка остаётся в логах.

**Исправление:** отдельный статус HTTP и причина отказа, проверка доступности overlay endpoint, понятное действие «Включить HTTP / изменить порт». Не показывать успешный результат подключения OBS лишь на основании WS.

## Захват, производительность и долговечность

### 13. P2 — цифровые события также ждут цикл опроса 125 Hz

**По коду.** `services/windows/raw_input.rs` (`run_raw_input`), `services/consts.rs:1`.

Перед чтением всего Raw Input buffer выполняется `sleep` с интервалом 8 мс. Клавиши и кнопки читаются там же. Поэтому комментарий диспетчера «Digital events are sent immediately» верен лишь после чтения буфера, но не для момента физического нажатия.

**Исправление:** событийное пробуждение capture thread, отдельно ограничивать частоту рассылки движения. Сначала измерить задержку и стоимость CPU; не обещать выигрыш без замеров. Проверять P50/P95/P99 от захвата до отрисовки, включая OBS.

### 14. P2 — перегрузка очереди сбрасывает состояние и теряет дистанцию

**По коду.** `ws_server.rs` (`INPUT_OVERFLOW`, `distributor`).

При переполнении очереди весь остаток отбрасывается и рассылается reset. Это спасает от зависших нажатий, но удерживаемая физически клавиша может исчезнуть до нового события, а накопленная в отброшенных пакетах дистанция теряется. Snapshot на этом пути автоматически не запрашивается.

**Исправление:** после overflow восстанавливать текущие удержания; учитывать движение/дистанцию отдельно от очереди цифровых событий. Добавить счётчик переполнений в разработческую диагностику. Текущий тест доказывает только ограниченную ёмкость очереди.

### 15. P2 — запись дистанции слабее записи основного документа

**По коду.** `studio_store.rs` (`persist_distance`).

Дистанция пишется напрямую в файл раз в три секунды, результат записи игнорируется. При сбое возможен повреждённый файл, который при старте превращается в 0. Временного файла/замены, как у конфигурации, здесь нет.

**Исправление:** атомарная замена, обработка ошибок, финальный flush при штатном завершении. Допустимую потерю последних секунд при аварийном выключении явно определить.

### 16. P2 — HTTP не ограничивает чтение заголовков и время запроса

**По коду.** `services/http_server.rs` (`serve`).

`read_line` читает запрос и заголовки без общего лимита, таймаута и ограничения числа соединений. По умолчанию сервис локальный, поэтому приоритет ниже проблем сохранения; при LAN-настройке поверхность воздействия шире.

**Исправление:** предел request line/headers, таймаут чтения и записи, ограничение активных соединений. Не требуется превращать локальный сервер в сложную веб-платформу.

### 17. P2 — стоимость продвинутых текстур ещё не измерена в худшем случае

**Риск.** `renderer/scene.ts` (`texture`, `renderCaps`).

Tile создаёт плоскость 9×9 относительно раскладки для каждой клавиши. Blur/glow/blend/filter и множество DOM-слоёв могут стоить значительно дороже простой линии. Настройки допускают 32 модуля и по 100 клавиш.

Минутный прежний тест измерял JS и память конкретной сцены. Он не доказывает малую стоимость GPU-композиции произвольной сцены с картинками.

**Проверка:** несколько реалистичных и предельных сцен в OBS, 1080p/1440p/4K, render lag, GPU time, память 30–60 минут. Только после замеров решать, нужны ли общая маска/Canvas и ограничения качества.

## Что улучшить в визуале и кастомизации

Это предложения развития продукта, а не объявленные критическими ошибки.

1. **Редактирование клавиатуры непосредственно на холсте.** Выбор клавиши кликом, drag/resize, выделение рамкой, несколько клавиш, выравнивание и одинаковые интервалы. Сейчас эти операции требуют чисел и списка клавиш.
2. **Назначение клавиши нажатием.** Кнопка «Нажмите нужную клавишу», человеческое имя и отдельный продвинутый VK. Учесть Esc для отмены и левый/правый модификатор. Это значительно важнее ещё одного декоративного эффекта.
3. **Общий рисунок для группы модулей.** Сейчас координаты картинки общие внутри одного keyboard/mouse-модуля. Для двух блоков клавиатуры рисунок настраивается отдельно. Ввести область применения «Модуль / Группа» и общую систему координат. Это расширение исходной идеи, а не утверждение, что текущая маска не работает.
4. **Довести редактор картинки до законченного рабочего инструмента.** В одном окне разместить позицию, цветокоррекцию, смешивание и opacity; добавить предпросмотр «покой / нажатие», центрирование, flip X/Y, увеличение просмотра и сравнение до/после. Разрешить видеть изображение целиком под маской с отдельной прозрачностью только в редакторе — так проще совмещать рисунок.
5. **Библиотека изображений.** Миниатюры, понятный бюджет размера, использование в профилях/пресетах, выбор уже загруженной картинки, замена одной картинки во всех связанных местах. Сейчас дедупликация есть в коде, но явного управления библиотекой нет.
6. **Управление наследованием.** Для отдельного параметра показывать «унаследовано / переопределено» и кнопку сброса. Добавить копирование оформления между клавишами и применение к выбранным. Сейчас проще удалить всю индивидуальную настройку, чем вернуть наследование одного поля.
7. **Действительно разные заводские композиции.** Factory layouts имеют одинаковые позиции и размеры; темы преимущественно меняют палитру, радиусы и эффекты. Нужны компактная FPS-композиция, вертикальная, минимальная для записи, более выразительная стримерская. Не ограничиваться новым названием цвета.
8. **Настоящие миниатюры пресетов.** Сейчас карточки нарисованы отдельно от реального Scene. Генерировать preview из конкретного пресета, включая пользовательские картинки, размеры и скрытые модули.
9. **Читаемость интерфейса.** Увеличить мелкие второстепенные надписи; сделать панели сворачиваемыми/изменяемыми по ширине; проверить 1366×768 и Windows 125–200%. Основной интерфейс англоязычный — добавить русскую локализацию, включая ошибки и справку.
10. **Удобная настройка состояний.** В редакторе принудительно показывать idle, pressed, частичную analog depth и scroll. Пользователь должен настраивать цвет/рисунок нажатия без одновременного удержания физической кнопки.
11. **Управление слоями.** Перестановка drag-and-drop вместо числового z, группы, скрытие/блокировка группы. Горячие клавиши для движения на 1/10 px, дублирования, удаления и возврата в кадр.
12. **Mouse Trail.** Отдельная прозрачность линии, более ясное объяснение Fixed Field/Follow, preview скорости и готовые сочетания цвета/толщины/свечения. Цвет скорости сейчас зависит от времени получения агрегированных пакетов; для более стабильного результата передавать длительность/время измерения с backend.

Для коронной функции сначала исправить границы при изменении gap и валидацию импортируемых изображений. Затем наиболее полезны общий редактор параметров, предпросмотр нажатия и единая картинка на группу модулей.

## Сборка и сопровождение

### 18. P3 — staging накапливает старые frontend-ассеты

**Воспроизведено.** `studio/scripts/stage.mjs`.

На момент проверки в `ws-server/src/studio/assets` было 44 файла, а в актуальном `studio/dist/assets` — 6. Скрипт копирует новые файлы поверх старых, но не синхронизирует удаления. Tauri может упаковывать лишние исторические bundles.

**Исправление:** собирать staging в новый каталог и заменять только заведомо сгенерированный каталог. Проверка: два последовательных build должны давать одинаковый набор актуальных файлов.

### 19. P3 — процедура выпуска отличается от локальной проверки

**По коду.** `.github/workflows/_build.yml`, `scripts/build-studio.ps1`.

CI запускает unit-тесты и сборку, но не browser/visual integration; Windows artifact содержит exe, тогда как локальная portable-поставка содержит также runtime DLL и документацию. Это не доказывает поломку MSVC-сборки, но процедуры не эквивалентны.

Packaging повторно использует существующую папку поставки и оставляет `source-UUID` каталоги. Нет обязательного manifest «версия → исходный commit → хэши → зависимости». Текущее рабочее дерево имеет много незакоммиченных изменений, поэтому один commit не идентифицирует поставку.

**Исправление:** единый выпуск из чистого checkout, staging поставки с нуля, manifest, проверка именно упакованного exe. Browser/visual checks включить в CI; OBS оставить отдельным Windows acceptance job при наличии среды. Зафиксировать версию Rust и использовать locked dependency resolution.

### 20. P3 — редактор слишком монолитен

**По коду.** `studio/src/main.tsx`, `studio/src/style.css`.

В одном файле находятся транспортные callbacks, сохранение, Undo, импорт/экспорт, формы, редактор сцены и страницы. Длинные однострочные JSX/CSS затрудняют ревью и делают частные проверки сложными.

**Исправление:** вынести document store/history/synchronization, страницы, свойства разных модулей и типизированные UI-поля. Добавить форматирование и линт. Не нужен большой монорепозиторий; достаточно небольших модулей с чёткой ответственностью. Удалить либо изолировать неиспользуемый updater.

## Какие проверки добавить

- Конфликт двух редакторов и offline/reconnect с несохранёнными изменениями.
- Квота localStorage, отказ записи диска, повреждённый backup, отказ последнего сохранения.
- Одинаковое принятие/отклонение конфигов TS и Rust; corpus для v1/v2.
- Предельный JSON с кириллицей: экспорт, импорт, WebSocket, native storage.
- Необычные ID, дубли, координаты вне сцены, повреждённые картинки.
- Lock через drag, числа, выравнивание и смену вида мыши.
- Gap 0/30, крайние размеры, Tile + rotation на узкой/высокой раскладке.
- Отказ HTTP bind при успешном WS.
- Overflow очереди: восстановление удержаний и сохранение дистанции.
- Большие изображения при непрерывном вводе: задержка, блокировки, квота, Undo.
- Реальная периферия: 1/2/4/8 kHz, все кнопки, оба Shift/Ctrl/Alt, unplug во время удержания, analog, сон/пробуждение, смена раскладки, несколько устройств.
- CS2/KovaaK/Aim Lab, полноэкранный режим, разные уровни привилегий, запись/стрим OBS, длительная сессия. Результаты нельзя подменять синтетическими событиями.

## Рекомендуемый порядок работ

1. **Надёжность:** ревизии и конфликты; единые лимиты; полная серверная валидация; развязка диска и input; понятные статусы сохранения.
2. **Точность редактора:** ID, bounds/gap, lock, проверка картинок, применимость полей, доступность HTTP.
3. **Удобство кастомизации:** прямое редактирование клавиш, назначение нажатием, история жестов, наследование и копирование стиля.
4. **Визуальное развитие:** улучшенный image editor, группа модулей с общей картинкой, настоящие миниатюры и разные композиции.
5. **Выпуск:** нагрузочная и аппаратная приёмка, единый packaging/CI, подписанная поставка при наличии сертификата.

Первые два этапа важнее добавления новых эффектов: они защищают уже созданные пользователем раскладки и оформление.
